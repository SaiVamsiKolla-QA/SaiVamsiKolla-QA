## How I work

I usually start by asking what can actually go wrong instead of immediately writing test cases.

For APIs, that often means trying missing, invalid, extreme, contradictory, or state-dependent data.

For AI features, I look at whether the output makes sense for the user's request and what happens when the system has incomplete or conflicting information.

For web applications, I care about whether automation is stable enough to trust in CI, not just whether a script can click through the page once.

And when something fails, I want more than a failed assertion. I use logs, traces, browser activity, network calls, and test data to narrow down where the problem started.
